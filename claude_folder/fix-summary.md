## What to do when deploying

1. **Create `config/database.local.php` before replacing any code.** Copy `config/database.example.php` and fill in the DB host, name, user and password and `base_url` (e.g. `https://siap.man2kotamadiun.sch.id`, no trailing slash). Ideally also set `app_secret`: generate it with `php -r "echo bin2hex(random_bytes(32));"`. `base_url` is required: without it the site shows the 503 page with "isi base_url di config/database.local.php". Without the file at all, the app falls back to `root` with no password, and the site also shows the 503 page. The new `config/database.php` no longer contains your values, so copy them over first. Rotate any database password that was ever committed (the history contains an old one).
2. **Run the migrations** in phpMyAdmin, in this order: `database/migration_akun_siswa.sql`, `database/migration_izin.sql`, `database/migration_keamanan.sql`. All three are safe to run again. Most of this is also created automatically if the DB user has CREATE/ALTER rights. Fresh installs only import `database/database.sql`.
3. **Nginx:** if the site runs on Nginx, use README §6. Part A goes into aaPanel's "URL rewrite" box; part B is for a hand-written server block. Then reload. On Apache/LiteSpeed the existing `.htaccess` files still apply. Afterwards, delete `database/*.sql` from the production server.
4. **Reverse proxy:** if PHP sits behind Cloudflare or another proxy, put the proxy's IP ranges in `trusted_proxies`. Otherwise every visitor appears to have the proxy's IP and could share one rate limit.
5. **Admins will be forced to change their password** on the next login if they still use a default password (admin123 etc.).
6. **Students re-bind automatically:** when a registered phone opens the home page, or completes a successful check-in, it receives the new cookie. Students do nothing. A phone normally becomes "active" at its successful check-in on the day after it received the cookie. Watch the "not yet migrated" count in Manajemen Perangkat. Once most devices have moved, the school can optionally set **"Batas pengenalan perangkat lama"** in Pengaturan; after that date, unmigrated devices need a reset. It is left empty on purpose so the school picks the date. After migration, a student who clears browser cookies (or switches browser or phone) needs a device reset from an admin, as before.
6a. **Login limits:** staff and students who log in from a network they have used successfully in the last 30 days aren't affected by the progressive delay. Someone on the *same* IP (e.g. the school NAT) can still lock a username from that IP for 15 minutes with 5 wrong passwords, or block that whole IP for 15 minutes with 300 failures. During a sustained attack, a staff member on a *new* network may not get a turn: the delay also applies to the right password, on purpose (letting the right password through would let every guess be checked). Log in from the usual network instead, or wait until the attack stops.
7. **Recommended once the screens are ready:** turn GPS on (with the real school coordinates) and turn off "QR Kelas permanen" in Pengaturan, then show the class QR on a screen or projector. The red warnings disappear once both are done.

## What was tested and how

Testing ran on PHP 8.3 (CLI and built-in web server) with MariaDB 10.11, using a small router script that copies the `.htaccess` rewrite rules. Everything below was run on `e5a1e9b` and the items marked *(re-review)* on the final head `f4d3cc5`. The parallel tests used the built-in server with 48 worker processes, so requests really ran at the same time; the same tests against the previous head reproduced the race.

- `php -l` passes on all 64 changed PHP files.
- **Schema:** imported the new `database.sql` into an empty database. Imported the **old** `database.sql` from `main`, then ran every migration twice. Both end with the same tables and no errors.
- **Student portal (C1):** with `base_url` written with a trailing slash, a student login goes to `/portal` (200), so the loop is gone. A sub-folder install (`/siap/`) sets the cookie path to `/siap/portal`.
- **Guards (I2/I3):** direct requests to `/includes/*.php`, `/config/database.php` and `/portal_siswa/*.php` return 404, and `/panel/*.php` redirects to the router. An operator without `izin.lihat` gets 403 on an attachment.
- **Login limits (I5):**
  - A forged `X-Forwarded-For` is ignored.
  - 5 wrong passwords from one IP lock that IP for 15 minutes.
  - After 100 failures from 100 different IPs, the admin can still log in from a known IP. An unknown IP gets a 1-second wait instead of a lock, and after 200 failures the wait is 32 seconds.
  - A NAT IP that made 20 failures on other usernames doesn't block the admin who is known on that IP.
  - Six addresses in one IPv6 /64 count as one IP (locked after 5); another /64 isn't affected.
  - A successful login removes only that IP's failures.
  - The portal records known IPs the same way.
  - *(re-review)* **Parallel requests**, new code vs previous head (password checks actually performed):
    - 40 simultaneous wrong passwords for `admin` from one IP: **5** (previous head: 40).
    - 40 simultaneous requests from 40 different IPs while the 60-second delay is active: **1** when a slot is free, **0** when it isn't (previous head: 40).
    - 40 simultaneous requests for 40 different staff accounts from one IP: **20**, the per-IP limit (previous head: 38).
    - Student portal, 40 simultaneous from one IP: **5** (previous head: 38); 40 IPs during the delay: **1** (previous head: 38).
    - A correct password still logs in. A failed portal activation code is counted, but a correct code with a too-weak new password and a successful activation are not. In the portal password change, only a wrong old password is counted.
  - *(re-review)* A known shared IP with 299 failures on other accounts still lets the admin in; at 300 it is locked for 15 minutes.
  - *(re-review)* `REMOTE_ADDR = ::ffff:198.51.100.9` is treated as `198.51.100.9` (same bucket as the plain address, a different mapped address is a separate bucket), including through a trusted proxy.
- **Forced password change (I6):** a fresh-install login with admin/admin123 redirects every page to Profil. Saving without a new password, or with admin123, or with fewer than 8 characters, is refused. After a valid change the dashboard loads. With a database user that has **no ALTER rights** on an old schema, the forced change still applies through the session fallback, and the dashboard warning says to run `migration_keamanan.sql`.
- **Device re-bind (H3):**
  - A copied UUID used in a check-in rejected for GPS leaves the legacy binding un-keyed.
  - The real phone's successful check-in makes it "pending".
  - A copied UUID after the student is already present (ALREADY_PRESENT) does **not** re-key.
  - If an attacker grabs a pending cookie through the home-page call, the real phone's next home-page call takes it back. The phone's next check-in with its cookie makes the binding "active", and after that a copied UUID is rejected for both check-in and passive calls.
  - A pending phone that lost its cookie can still check in with its UUID.
  - With the cut-off date in the past, UUID-only check-in is rejected; with a future date, it is accepted.
  - New registrations are active immediately.
  - *(re-review)* One-session takeover is closed: a copied UUID gets a passive cookie through the home page and immediately checks in with it. The binding stays pending, the cookie is swapped for a check-in cookie, and repeating the check-in the same day doesn't activate it. The real phone (UUID only) can still check in. On the next day the real phone's check-in makes it active, and the attacker is then rejected (MISMATCH). A passive cookie from yesterday, and a pending row of unknown origin, are both swapped rather than activated.
  - *(re-review)* The new columns are added by the app at runtime on an old database, and `migration_keamanan.sql` adds them and runs twice cleanly on the old schema and on a fresh install.
  - On an upgraded old database, the passive call and a check-in through a printed class QR (permanent mode) migrate the device correctly. GPS and QR settings are left unchanged.
- **Class QR (H3):** signed tokens are accepted. Tampered, expired, far-future and post-Regenerate tokens are rejected, and raw printed tokens are rejected in signed mode. A full check-in through a signed class QR works.
- **Config (minors):** with no local config, the 503 incident text and the log say `config/database.local.php` hasn't been created.
- *(re-review)* **Missing base_url**, run under PHP-FPM (FastCGI, no `server_name`, forged `Host: evil.example`): the page is a 503 whose incident text says "isi base_url di config/database.local.php". API calls get JSON code `CONFIG_MISSING`. The previous head redirected the same request to `http://localhost/login.php`. With `base_url` set, the redirect goes to the configured address.
- **Panel:** 32 admin pages return 200 or the expected redirect, with no PHP warnings. Manajemen Perangkat shows the not-yet-migrated count. Pengaturan saves the cut-off date, and the device page then shows it.
- **Not tested:** Nginx and the aaPanel URL-rewrite box (no Nginx here; checked by reading), Apache, MySQL 8 (`GET_LOCK` behaves the same there), real phones or the Android WebView, and HTTPS.

## Left unfixed, and why

- **I4 (staff can't record izin/sakit for a student):** this is a new feature, not a contained fix. It needs a student picker, a decision on whether to skip the 3-day back-dating limit and the attachment rule, auto-approval and notification. The school should decide those rules first.
- **IP-validation setting (earlier M1):** making it enforced needs an "allowed IPs/CIDR" list setting and a policy decision (students on mobile data would be blocked). The toggle is already labelled "(informatif)" in Pengaturan. Not changed.
- **Minors #2, #4, #5, #6** (dead `portal_siswa/masuk.php`, the back-dated sickness rule, the bulk-approve warning, Google Fonts vs the "no CDN" claim): out of scope for this branch.
- **Known limits of the new device binding:** a student who deliberately exports their own cookie to a friend's phone can still share attendance; GPS and signed class QRs are the counter to that. Until a device is "active" (or until the optional cut-off date), someone with a copied UUID can still check in as that student, as before the fix. To take over the binding they need fully successful check-ins (valid QR, opening hours, inside the GPS radius; GPS coordinates come from the phone) on two different days with no check-in from the real phone in between. Setting the cut-off date closes this window; the date is left empty for the school to choose.
- **Known limits of the login protection:** a person on the same IP as a staff member can lock that username from that IP for 15 minutes with 5 wrong passwords. During a sustained distributed attack, someone logging in from a new network may not get a turn, because an attacker sending one attempt per slot uses every slot (up to 60 seconds each). The right password is deliberately not let through during the delay, since that would make the delay useless. A known network is not affected.
- **Classroom QR screen needs a panel login** (raised in the pre-merge review): a classroom device showing the signed QR has to stay logged in to the panel. A separate read-only display link per class would be better, but it is a new feature and isn't included.
- `uploads/siswa/siswa_b0a980573f44b475.png` (the school logo) is still tracked. It isn't personal data, and new uploads are ignored from now on.
